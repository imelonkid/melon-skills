# 文章审阅

> 依赖的路径全部来自环境变量（定义在 `~/.zsh/conf.d/ops.zsh`）：`$BLOG_REPO` 博客仓库、`$BLOG_VAULT` Obsidian 笔记仓库、`$BLOG_SRC` 草稿目录。
> 先 `zsh -ic 'echo $BLOG_REPO $BLOG_VAULT'` 确认，缺了就提示用户，**不要猜路径**。审阅脚本（`review-scan.mjs`、`review-diff.mjs`）在博客仓库里，不在本 skill 里。

审阅 Obsidian `写点东西/` 目录下的博客草稿。**只给建议，不直接改文件**，除非用户明确要求。

## 〇、两条铁律

**一、笔记是唯一事实来源。** 线上文章由 Obsidian 笔记同步生成，
`src/content/posts/` 下的文件是产物，不是稿子。

要改文章内容，**永远先改笔记，再同步发布**。绝不直接改 `src/content/posts/`——
那里的改动下一次 `pnpm run sync` 就会被覆盖，而且笔记和线上会悄悄分叉。

**二、改动必须先落成待审 commit，让用户看 diff。**

笔记目录本身是 git 仓库（`$BLOG_VAULT`）。你按建议改完之后不要直接发布，
而是在笔记仓库里提交一次，把 diff 交给用户过目。用户点头才继续同步上线。

理由很简单：审阅的产出是"建议"，采不采纳是作者的事。diff 是最诚实的呈现方式——
改了哪一行、删了什么，一目了然，比你在对话里复述准确得多。

## 一、先确定审哪几篇

**第一件事是看笔记仓库的历史，找到上次发布的基线。**

```bash
git -C "$BLOG_VAULT" log --oneline -8 -- "写点东西"
git -C "$BLOG_VAULT" tag --list 'pub/*' --sort=-creatordate | head -3
```

`pub/YYYYMMDD-N` 是发布 tag，每次成功上线后自动打的，代表**这个笔记状态
已经在线上了**。所以：

> 审阅的范围 = 最新的 pub tag → 现在

tag 之前的内容审过也发过了，别再看第二遍；tag 之后的（包括还没提交的改动）
才是这次要审的增量。

```bash
git -C "$BLOG_VAULT" diff --stat "$(git -C "$BLOG_VAULT" tag --list 'pub/*' --sort=-creatordate | head -1)" HEAD -- "写点东西"
git -C "$BLOG_VAULT" status --porcelain -- "写点东西"     # 还没提交的
```

然后跑扫描脚本，它会把 tag 和逐篇哈希两件事合起来告诉你：

```bash
cd "$BLOG_REPO" && node scripts/review-scan.mjs
```

输出会先报「上次发布：pub/… / 自那以后动过 N 篇」，再列出待审文章。

输出的就是待审文章的完整路径。**不要自己遍历目录**——脚本按正文 SHA-1 比对，
已审过且没改动的会自动跳过，这是"不重复分析"的关键。

- 用户要求全部重审：加 `--all`
- 想看整体状态：`--status`
- 只审某几篇：直接读用户指定的文件，跳过这一步

若输出「没有需要审阅的文章」，如实告诉用户，不要硬找活干。

**想知道用户这次改了什么**，用笔记仓库的 commit 对比，比逐字读全文高效得多：

```bash
git -C "$BLOG_VAULT" log --oneline -5 -- "写点东西"
git -C "$BLOG_VAULT" diff HEAD~1 HEAD -- "写点东西"      # 上一次改动
git -C "$BLOG_VAULT" diff HEAD -- "写点东西"             # 尚未提交的改动
```

如果 `写点东西/` 还有未提交的改动，说明用户刚动过笔记。先看 diff 再决定
从哪读起——只有 diff 看不出上下文时，才回头读全文。

## 二、逐篇审阅

对每篇文章按下面四类检查。**每条问题都要给出原文和改法**，不要只说"这里可以更好"。

### 1. 错别字

中文高频混淆，逐一核对：

| 易错 | 辨析 |
|---|---|
| 的 / 地 / 得 | 定语用「的」，状语用「地」，补语用「得」 |
| 在 / 再 | 「在」表处所或进行，「再」表重复 |
| 做 / 作 | 具体动作用「做」，抽象搭配用「作」（作出决定、做饭） |
| 像 / 象 | 比喻用「像」 |
| 账 / 帐 | 钱财用「账」，布幔用「帐」 |
| 既 / 即 | 「既然」「既…又」用既；「即刻」「即使」用即 |
| 己 / 已 / 巳 | 自己 / 已经 |
| 需 / 须 | 「需要」用需，「必须」用须 |

技术文另外注意：产品名和术语的大小写（GitHub 不是 Github、JavaScript 不是 Javascript、
MySQL 不是 Mysql、Nginx 不是 nginx 开头句）。

### 2. 语病

- **成分残缺**：主语被介词吞掉（「通过这次实践，使我明白了…」——删「通过」或「使」）
- **搭配不当**：「提高速度」对，「提高效率」对，「提高水平」对，但「提高问题」不对
- **啰嗦**：「进行一个 X 的操作」→「X」；「的的不休」；「其实说实话」
- **语序**：状语位置、多重定语顺序
- **中英混排**：中文与西文之间缺空格（本站惯例是加空格）；全角半角标点混用

### 3. 文笔与风格

这是重点。本站的调性是**克制、具体、有人味**，技术文也一样。判断标准：

**具体物优先于抽象概括。** 这是最重要的一条。
- ✅「相机导出的照片全是 IMG_4821 这种名字，找起来很痛苦」
- ❌「文件命名不规范会影响使用体验」
- ✅「修车铺的师傅收摊前会把工具一件件擦干净」
- ❌「生活中有很多值得留意的细节」

看到抽象概括，就问：能不能换成一个具体的东西、一个时间、一个数字、一个画面？

**技术文要有「人」。** 为什么做这件事、什么地方卡住了、当时什么感受。
纯步骤罗列可以发，但缺一层。开头一句真实的动机往往就够。

**避免 AI 腔。** 这类痕迹要指出来：
- 「首先…其次…最后…」「总而言之」「综上所述」
- 「在当今这个 X 的时代」「随着 X 的不断发展」
- 每段都用破折号做转折，或每段都是三句排比
- 结尾强行升华成人生感悟
- 形容词堆砌而不落到实处（「深刻的」「巨大的」「极其重要的」）

**长短句交错。** 通篇长句会闷，通篇短句会碎。读一遍，把连续三个以上同长度的句子标出来。

**结尾不要用力。** 本站的好结尾是收束而非拔高：
「工具不必大，能省下每次三分钟的翻找，就值得写。」
而不是「让我们一起在技术的道路上不断前行」。

### 4. frontmatter

对照 `src/content.config.ts` 的 schema：

- `title` 必填
- `date` 必填，`YYYY-MM-DD`。**这是发表日，文章上线之后就不要再改。**
  它决定首页排序和 RSS 的 `pubDate`——改了会让老文章跳回首页顶部、
  让订阅者收到一次重复推送，等于骗读者
- `updated` 实质修改日，**不用手填**。执行 `--mark` 时，如果这篇已经上线过
  且正文哈希变了，会自动写回 Obsidian。页面上显示成「更新于 X」。
  如果这次改动只是错别字、不值得标更新，跟用户确认后把这行删掉即可
- **`tag` 是硬卡控项，见下面「标签」一节**
- `publish` 是 `true` 才会被发布——如果用户说"这篇要发了"但字段还是 false，提醒他
- `draft: true` 的文章**只在本地 dev 可见，不进构建产物、不上线**。这是本站
  用来做本地预览的机制：想验证排版、公式、图表效果又不想发布时，写一篇
  `draft: true` 的文章放在 `src/content/posts/` 下即可（注意这是博客仓库里的
  文件，不是 Obsidian 目录）。站上现有 `_demo-math-mermaid.md` 就是这样一篇
  常驻的渲染样例。审阅时遇到 `draft: true` 的文章，按草稿对待，不必催发布
- `slug` 决定网址，留空则用文件名（中文文件名会被转成中文网址，能用但不好看，
  技术文建议给英文 slug）
- `excerpt` 留空会自动取正文首段——检查首段是否适合当摘要，不合适就建议手写

### 5. 标签（硬卡控）

标签有两条规则，**违反会让构建失败，文章根本发不出去**。审阅时必须检查，
不要等用户跑 `blog-deploy` 才发现。

先读白名单：

```bash
cat "$BLOG_REPO/src/tags.ts"
```

**规则一：视觉宽度不超过 8**（汉字算 2，即最多 4 个汉字）。
超了直接告诉用户改，并给出替换建议——通常是砍成更粗的分类：
「分布式事务一致性」→「分布式」，「计算机原理」→「原理」。

**规则二：必须在白名单里。**

遇到不在白名单的标签，**默认立场是不新增**。按顺序做三件事：

1. **先找现有标签能不能覆盖。** 「运维」能不能归到「技术」？「后端」能不能
   归到已有的语言标签？大多数情况能——白名单里 20 多个标签已经覆盖了这个
   博客的绝大部分主题。
2. **确实覆盖不了，再考虑新增。** 判断标准是：这个标签**将来还会有第二篇、
   第三篇文章**吗？只服务于当前这一篇的标签不该存在——它不是分类，是标题的
   一部分。站上曾经有 70 个标签，其中 48 个只有 1 篇文章，那样的标签体系
   等于没有分类。
3. **要新增就明确告诉用户**：需要在 `src/tags.ts` 的 `TAGS` 里加一行，
   并说明为什么现有标签不够用。让用户点头，不要自作主张加进去。

**标签膨胀是慢性病**，每次都觉得"就多这一个"，一年后就是七十个。审阅时
宁可让用户用一个不那么精确的现有标签，也不要轻易开新的。

### 6. 图片（必查）

图片是这个博客栽过跟头的地方，**每篇都要核对，不能凭肉眼看 Obsidian 里显示正常就算过**。

Obsidian 里图片显示得好好的，同步到博客却可能丢——最常见的原因是**你在
Obsidian 里挪动过附件**。挪完它会把链接从 `![[图.png]]` 悄悄改写成
`![[Assets/图.png]]`，而同步脚本一度只按文件名匹配，带上目录就找不着了。
2026-09-05 就这么丢过一张图，本地和线上都没有，直到肉眼看文章才发现。

现在有两道防线，审阅时**跑一遍确认**：

```bash
cd "$BLOG_REPO" && pnpm run sync && pnpm run preflight
```

- `sync` 遇到找不到的附件会**非零退出**，不再只打一行警告
- `preflight` 会核对正文里每个 `/images/...` 引用在 `public/` 下真实存在

除了跑脚本，人眼再确认三件事：

- **配图有没有说明。** `![](图.png)` 这种空 alt，对读者和搜索引擎都是浪费。
  Obsidian 里写 `![[图.png|这里是图注]]`，竖线后面的文字会变成 alt
- **配图是不是够。** 长文只有文字会闷。讲架构的地方配一张结构图，讲界面的
  地方配一张截图，比三段描述有效
- **截图里有没有不该露的东西。** 内部系统名、同事姓名、真实数据、水印里的
  工号——发出去就收不回了

如果 preflight 报了断链，**不要往 `.image-exceptions.json` 里加**。那个文件只
记录 2017 年迁移时源头就丢了的老图，新文章断链一定是同步或路径出了问题，去修。

## 三、报告格式

每篇一个小节，问题按严重程度排序（错别字/语病在前，风格建议在后）：

```
## 文章标题.md

**错别字**（2 处）
- 第 3 段「他做出了巨大的贡献」→「作出」：抽象搭配用「作」
- 第 7 段「在来一次」→「再来一次」

**语病**（1 处）
- 第 5 段「通过这次排查，让我发现…」：主语被吞。改「这次排查让我发现…」

**风格建议**（按价值排序）
- 第 2 段整段是抽象概括，建议换成具体场景。原文「配置过程比较繁琐」，
  可以写成当时卡了多久、卡在哪一步。
- 结尾「希望这篇文章对大家有帮助」是套话，建议删掉或换成一句自己的判断。

**标签**
- `tag: 运维` 不在白名单。建议用现有的「技术」——这篇讲的是服务器加固，
  和站上其他技术文属于同一类，没必要单开一个分类。

**frontmatter**
- `publish` 仍是 false
```

没问题的篇目也要说一句「未见明显问题」，不要略过——用户需要知道每篇都被看过了。

## 四、审完之后：先落 commit，再让用户看 diff

**报告给用户看过、用户同意按建议修改之后**，流程是固定的四步：

**第 1 步，确认笔记仓库是干净的。**

```bash
git -C "$BLOG_VAULT" status --porcelain -- "写点东西"
```

有未提交改动就先问用户：这些是他自己写的、还是上次审阅遗留的？
**不要把用户的改动和你的建议混进同一个 commit**——那样 diff 就没法看了。
需要的话先替他提交一次基线。

**第 2 步，改笔记，不改 `src/content/posts/`。**

**第 3 步，在笔记仓库里提交一次待审 commit。** 消息里说清楚改了什么、为什么改：

```bash
git -C "$BLOG_VAULT" add "写点东西"
git -C "$BLOG_VAULT" commit -m "review: <文章名> 的修改建议（待审）

机械问题：
- …

内容：
- …"
```

然后**生成 HTML diff 页面并发给用户**——不要让他去命令行看：

```bash
cd "$BLOG_REPO" && node scripts/review-diff.mjs HEAD~1 HEAD
```

页面写到 `.review/`（已 gitignore，只作本地发布记录）：按日期归档一份，
外加一份 `latest.html`。用 SendUserFile 把 `latest.html` 发过去。

这个页面做了**逐字对比**——中文散文改几个字，`git diff` 会整行标红整行标绿，
眼睛得自己找差在哪；这里只高亮真正变动的字符。这是它值得存在的唯一理由，
所以别退回去用 `--stat` 或者在对话里复述改动。

范围参数按需给：改动跨了几个 commit 就 `HEAD~3 HEAD`，只看某一次就
`HEAD~2 HEAD~1`。

**第 4 步，用户点头之后再发布。** 发布成功后 `deploy.sh` 会自动在笔记仓库打一个
`pub/YYYYMMDD-N` tag，作为下次审阅的基线。**失败就不打**——否则基线指向一个
从没上线的状态，下次会漏掉真正的增量。 用户要是不满意，`git revert` 或者按他的意见
再改一版，重新提交——不要在对话里反复口头描述改动。

## 五、记录审阅状态

**每篇文章上线前都要过这个 skill，没有例外。** `preflight` 会检查审阅记录，
标了 `publish: true` 却没审过、或者审完又改了正文的，直接挡住发布——所以
"先发了回头再看" 这条路是走不通的，这是故意的。

**先把报告给用户看**，问要不要按建议修改。用户同意后再改文件。

无论是否修改，都要把审过的篇目记录下来，否则下次会重复分析：

```bash
node scripts/review-scan.mjs --mark "文件名1.md" "文件名2.md"
```

这一步除了记哈希，还会**自动给已上线的文章写 `updated`**（正文变了才写）。
输出里会明说写了哪篇、写成哪天。

注意：**还原一次改动也算改动**。把正文改回原样再 `--mark`，同样会盖上
`updated` ——这是对的（内容确实动过两次），但如果你只是在做实验，
记得手动把那行删掉。

**注意**：如果你按建议修改了正文，改完之后再执行 `--mark`——哈希以最终内容为准。

## 边界

- 不要为了凑数而提建议。文章本来就好，就说好。
- 风格建议是建议，用户拒绝就不要坚持。这是他的博客，他的声音。
- 不要把所有文章都改成一个腔调。用户自己的语感（长句、铺陈、由具体景物起兴）
  是特点，不是缺点。
